# ble-uart-serial (variant A: USB CDC <-> BLE)

The board shows up on the PC as a USB virtual COM port (`/dev/ttyACM0`, like `hello-cdc`; USB DP/DM, no
GPIO to pick). Bytes sent to that port go to the BLE central as GATT notifications; bytes the central writes
go out of the port. SDK/Bluetooth logs share the same port as `[BT] ...` lines.

Tags used below: **[compiled]** built/linked in the scratch harness with the real `scripts/apply_app.py`;
**[untested]** no hardware here, never run; **[assumed]** inferred from SDK source or habit, not checked.

## What it is
- SDK `trans_data` BLE example, minimal changes (`overlay/`, regenerated by `patch/gen_overlay.py` from the
  pristine SDK, diffs in `patch/*.diff`). Default UUIDs: GATT service `ae30` (the advertisement lists 16-bit UUID `af30`, seen on hardware), **ae01 = PC<-BLE (write /
  write-without-response)**, **ae02 = PC->BLE (notify)**, plus the stock ae03/ae05/ae10 characteristics.
- One deviation from "default UUIDs": ae01 property is changed from write-without-response only to
  write-without-response **and** write (with response), so both kinds of write are accepted. UUIDs/handles are unchanged. [compiled] [untested]
- Name: `JL-UART-BLE`. Config: `TCFG_USER_BLE_ENABLE 1`, `TCFG_USER_EDR_ENABLE 0`, 512K flash, SDK UART0 (PA0) log off,
  `LIB_DEBUG 1` so library logs exist (the board Makefile's `-DCONFIG_RELEASE_ENABLE` otherwise turns them off).
- Shared core `src/uart_bridge.{c,h}` (CDC <-> rings <-> chunking <-> logs), **byte-identical** in both variants:
  `sh scripts/check-shared-core.sh`. It is installed over the unused SDK file
  `apps/spp_and_le/examples/nonconn_24g/ble_24g_deal.c` (new .c files cannot be added to the fixed Makefile list) and
  `apps/spp_and_le/include/uart_bridge.h`. Edit only `firmware/shared/uart-bridge/`, then `sh scripts/sync-uart-bridge.sh`.
- BLE glue (the only transport-specific code): `bridge_bt_send()` and the hooks in `ble_trans.c`.

## Behaviour
- **PC -> BLE:** CDC OUT endpoint -> ring A (2048 B) -> chunks of ATT MTU-3 bytes (20 until the MTU exchange completes; reset to 20
  on every connect) -> `ble_comm_att_send_data()` notify on ae02. "Ready" = connected **and** the central enabled notifications (CCC).
- **BLE -> PC:** write on ae01 -> `bridge_bt_rx()` -> ring B (2048 B) -> CDC IN.
- **Flush on idle:** a partial chunk is sent once no new byte arrived for >= 1 OS tick; **1 tick = 10 ms** (HZ 100), the check is
  tick-quantised, so the real delay is 10-20 ms. A partial chunk is also forced out after 5 ticks (50 ms) of continuous input. Full chunks go immediately.
- **No peer / notifications off:** CDC data is **dropped and counted** (not buffered). On disconnect ring A is flushed (counted as dropped).
- **Overflow:** ring full -> the new bytes are dropped and counted; reported in the periodic stats line. No backpressure to the PC.
- **BLE stack busy:** chunk stays queued and is retried on the next `CAN_SEND_NOW` event or tick.
- **After disconnect** the example's `adv_auto_do = 1` re-advertises [assumed, from SDK source] [untested].
- **Pairing:** none in this config (the example uses no security requirement); connections are unencrypted "just connect" [assumed from the example's SM config] [untested].
  `[BT] pairing/encryption` lines appear if the central starts encryption.

## Log format
Every log source (`log_print`, `printf`, `puts`, `putchar`, `put_buf` hexdump 16 B/line, bridge events) is queued as whole records and
written to the CDC port **between data chunks**, never inside one. Format: `[BT] [tag ]text\r\n`. If the data stream is mid-line a `\r\n` is
inserted first. Embedded newlines split into several records, ANSI colour escapes are stripped. Lines are dropped whole if the 3 KiB log ring is full
(a dropped-lines count is reported). Lines caused by the CDC write itself (USB driver traces) are discarded to avoid a feedback loop.
Periodic `[BT] app: stats ...` line (every 5 s, only if counters moved): bytes both ways, drops by reason, chunk size.

## Switches (edit `firmware/shared/uart-bridge/uart_bridge.h`, then sync)
| switch | default | meaning |
|---|---|---|
| `BRIDGE_CDC_LOGS` | 1 | **0 = no logs on CDC, byte-clean data stream** (overrides stay, nothing reaches PA0) |
| `BRIDGE_LOG_MIN_LEVEL` | 0 | drop `log_print` below this level (0 verbose .. 4 error) |
| `BRIDGE_RX_VIA_SDK_READ` | 0 | read CDC with `cdc_read_data()` instead of direct `usb_g_bulk_read()` |
| `BRIDGE_BT_STACK_DEBUG` | 1 | strong `ble/l2cap/profile/rfcomm_debug_enable` (btstack internal traces) |
| `BRIDGE_RING_A/B/LOG_SIZE`, `BRIDGE_IDLE_TICKS`, ... | see header | sizes and timing |

## Size (scratch harness, 512K config) -- full table in `docs/uart-bridge-comparison.md`
text 133384 + data 19096 (app.bin 152520 B), bss 19656. Core static RAM 8734 B (rings 7168 + buffers) plus two task stacks of 512 x 4 B = 2 KiB each [assumed to come from the OS heap]. [compiled]

## Known risks / not verified
- Interrupt-off time while copying a log record (<= 200 B) into the ring, and in the format-buffer claim: not measurable here. [untested]
- Direct `usb_g_bulk_read()` on the OUT endpoint (bypasses the SDK's cdc read path) is **assumed safe**; fallback switch above. [assumed]
- `cdc_set_wakeup_handler` is re-asserted ~1/s from the task because `cdc_release()` drops it. [assumed to be enough]
- `usb_g_bulk_write` blocking time with a stalled host is unknown; only the B2C task can block, C2B keeps running (data is then dropped by ring B overflow). [untested]
- Task stack size (2 KiB) vs `vsnprintf` depth in the log path is not measured; logs from other tasks also use the caller's stack. [untested]
- BLE throughput, MTU behaviour, re-advertising and CCC handling on a real central: all [untested on hardware].
